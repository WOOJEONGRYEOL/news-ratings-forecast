# 종편 4사 메인뉴스 시청률 예측

채널A `뉴스A` · JTBC `뉴스룸` · MBN `뉴스7` · TV조선 `뉴스9` 의 **가구/2049 시청률**을
향후 7일까지 예측하고, 편성·야구·날씨·연휴 조건을 바꿔가며 시뮬레이션하는 대시보드.

```bash
./run.sh              # 대시보드 (http://localhost:8501)
./daily_update.sh     # 시트 갱신 → 모델 재학습 → KBO·기상 캐시 갱신
```

### 운용 시점 — 첫 예측일은 보통 '오늘'이다

시청률 데이터는 **매일 아침 전날치**가 들어온다. 그래서 마지막 관측일은 어제이고,
예측 구간은 `어제+1 ~ 어제+7` = **오늘부터 7일**이다. 아침에 열어 **오늘 저녁 방송**을
판단하는 게 이 대시보드의 주 용도다.

- 대시보드는 첫 예측일을 `오늘(08/29 Sat)` 처럼 **실제 날짜와 상대 시점**으로 표시한다.
  (한때 무조건 "내일(D+1)" 로 적었는데, 운용 방식과 하루 어긋난 표기였다.)
- 데이터가 2일 이상 지연되면 헤더와 예측 화면에 경고가 뜬다.
- 사이드바 **⬇️ 데이터 갱신** 으로 앱 안에서 시트를 다시 받을 수 있다.

`daily_update.sh` 를 cron 에 걸면 아침마다 자동으로 돈다.

```
10 8 * * * /Users/woo/FORECAST/daily_update.sh >> /Users/woo/FORECAST/logs/daily.log 2>&1
```

데이터 원본은 구글 시트다. `sync_data.py` 가 CSV 로 내려받아 **파싱과 행 수를 검증한 뒤에만**
교체한다(시트가 깨졌을 때 기존 데이터를 날리지 않게). 시트 ID 는 `scripts/sync_data.py` 상단에
있고, `--url` 로 다른 소스를 지정할 수도 있다.

## 2. 모델링에서 신경 쓴 것

### 지평별 직접 예측 (재귀 예측 아님)
D+1 예측값을 D+2 입력으로 되먹이면 오차가 누적된다. 대신 **지평 h마다 전용 모델**을 두고,
그 모델의 자기회귀 피처를 전부 `shift(h)` 이상으로 만든다. D+7 모델은 어제 시청률을 아예
보지 않는다 — 실제로 D+7을 예측하는 시점엔 알 수 없는 값이기 때문이다.

### 두 가지 운용 모드 — 예측은 한 번만 내는 게 아니다

KBO 는 보통 경기 시작 1~2시간 전(17시 전후)에 우천취소를 발표하고, 종편 메인뉴스는
18:50 ~ 21:00 에 나간다. **그 사이에 몇 시간의 창이 있다.** 그래서 예측을 두 시점에 낸다.

| 모드 | 언제 | 외생 변수 | 쓰임 |
|---|---|---|---|
| **사전 예측** | 전날 (기본) | 편성은 알고 **취소는 모른다** | D+1 ~ D+7 주간 계획 |
| **당일 수정** | 대상일 낮 | 취소까지 **확정된 값** | 그날 저녁 방송 대비 |

두 모드 모두 **시청률 시차 피처는 마지막 관측일까지만** 쓴다 (`horizon` 이 통제).
`as_of` 는 외생 변수의 관측 시점만 옮기므로 타깃 누수가 아니다.

```bash
.venv/bin/python run_backtest.py --folds 10            # 사전 예측 성능
.venv/bin/python run_backtest.py --folds 10 --same-day # 당일 수정 성능
```
두 결과의 차이가 **"우천취소를 아는 것의 가치"** 다. 대시보드에서는 사이드바
`🕑 운용 모드 → 당일 수정` 토글로 전환하고, 사전 예측 대비 변화량을 함께 보여준다.

### 우천취소는 실제로 시청률을 움직인다

분 단위 시청자 유출입에서 야구 중계 채널로의 이탈이 보인다는 현장 관찰이 있었고,
일별 데이터에서도 확인된다. 취소는 같은 요일·같은 계절 안에서 변하므로 자연 실험이 된다.

같은 요일 평균 대비 비율 (시즌 중 편성일 604일):

| 취소 경기 | n | 뉴스A | JTBC | MBN | TV조선 |
|---|---:|---:|---:|---:|---:|
| 0경기 | 486 | 0.979 | 0.992 | 0.981 | 0.981 |
| 1경기 | 52 | 1.076 | 0.982 | 1.059 | 1.097 |
| 2경기 | 36 | 1.006 | 1.077 | 0.989 | 0.984 |
| 3+경기 | 30 | **1.198** | 1.073 | **1.212** | **1.152** |

취소가 많을수록 단조 증가한다. 뉴스A +10.6%, MBN +9.5%, TV조선 +9.5% 는 유의하고
**JTBC 만 유의하지 않다** (+4.2%, ±7.0) — 2049 비중이 높아 야구 시청층과 덜 겹친다.

**주의:** 취소는 비 때문에 생기고 비는 그 자체로 재택 시청을 늘린다. 이 추정치는
'야구 이탈 + 강우' 합이지 야구만의 효과가 아니다. 분리하려면 실측 강수 데이터가 필요하다.

모델의 당일 수정 폭도 같은 방향이다 (2026-08-28, 5경기 전부 취소):

| 방송사 | 사전 예측 | 당일 수정 | 변화 |
|---|---:|---:|---:|
| MBN 뉴스7 | 1.280 | 1.439 | **+12.4%** |
| 채널A 뉴스A | 1.509 | 1.613 | +6.9% |
| JTBC 뉴스룸 | 2.533 | 2.692 | +6.3% |
| TV조선 뉴스9 | 1.956 | 2.044 | **+4.5%** |

19시대 3사가 21시대 TV조선보다 크게 반응한다. 2049 지표는 거의 움직이지 않는다(+0~2%).

이 수치는 **편성 기준 통일 이후** 값이다. 학습만 사후값(실제 진행 경기 수)을 쓰던
버전에서는 같은 상황에서 MBN 이 +4.9% 로 나왔다 — 변수 의미가 어긋나면 효과가
절반 이하로 죽는다.

### 미래에 알 수 있는 값만 외생 변수로
공휴일·요일·일몰 시각·KBO **편성**은 예측 시점에 확정돼 있다. 반면 당일 기사량이나
**우천취소**는 사전 예측 시점에 알 수 없다.

여기서 한 번 데였다. 원본 일정 JSON 에는 경기가 끝난 뒤의 취소 여부가 들어 있어서,
`kbo_games`(취소되지 않은 경기 수)를 그대로 쓰면 **"내일 비가 와서 5경기가 다 취소된다"**
는 걸 미리 아는 모델이 된다. 실제로 2026-08-28 은 5경기 편성이 전부 취소된 날인데
피처는 `kbo_games=0` 으로 계산되고 있었다. 두 가지로 고쳤다.

- 경기 수·시작시각·중첩시간은 **학습·추론 양쪽 모두 편성 기준**으로 통일했다.
  학습만 사후값을 쓰면 변수의 의미가 조용히 어긋난다.
- 취소 수(`kbo_cancelled`)는 `as_of` 로 시점을 게이팅한다. 사전 예측에서는 0(=아직 모름),
  당일 수정에서는 확정값.

기온은 계절 근사치 `temp_proxy` 로 대체돼 있다 — 실측 API 연동 지점을
`features.temperature_proxy` 에 열어 뒀다.

### KBO는 실제 일정을 쓴다 — 캐시 + 실시간 API 2단

`data/kbo_games/games_YYYY_MM.json` 에서 **실제 시작시각·우천취소·구장**을 읽는다.
이 파일은 **이 프로젝트가 직접 수집한다** (`scripts/sync_kbo.py`) — 외부 프로젝트
수집에 의존하면 그쪽이 멈출 때 조용히 낡는다. `~/kbo-forecast/data/` 가 있으면
함께 읽어 과거 시즌(2021~22)을 보완한다. 요일 기반 휴리스틱은 2026시즌을 못 맞춘다 — 평일 시작이
18:30·19:00 으로 섞여 있고, 8월 한 달에만 우천취소가 41건이다.

생성 변수: 경기 수, 취소 수, 서울 구장(잠실·고척) 경기 수, 최초/주력 시작 시각,
19시대·21시대 뉴스 방송 구간과의 **겹침 시간**, 포스트시즌 여부.

#### 캐시가 끝난 구간은 실시간 API 로 채운다

캐시는 수집 시점까지만 있다. 그 뒤 예보 구간을 요일 휴리스틱으로 메우면 크게 틀린다.
네이버 공개 API 는 **약 4주치 미래 편성**을 주므로 그걸 쓴다 (`kbo.fetch_live_daily`).

2026-08-29 기준 24일 중 **15일이 휴리스틱과 달랐다.**

| 날짜 | 휴리스틱 | 실제 | 영향 |
|---|---|---|---|
| 09-06 (일) | 5경기 14:00 | 5경기 **17:00** | 19시대 겹침 **0 → 1** |
| 09-13 (일) | 5경기 14:00 | 4경기 **17:00** | 19시대 겹침 **0 → 1** |
| 09-17 (목) | 5경기 | **2경기** | 시즌 막바지 편성 축소 |
| 09-24~25 (목·금) | 18:30 | **17:00** | 평일인데 오후 경기 |

일요일 시작 시각(14:00 vs 17:00)은 19시대 겹침을 0 ↔ 1 로 뒤집는다 —
일요일 뉴스 예측이 통째로 달라진다.

#### 중계권 체제 변경 — 2024 시즌부터 야구 변수를 분리한다

2006~2023 년은 네이버 컨소시엄이 KBO 를 **무료 온라인 중계**했고,
2024~2026 년은 **티빙 유료 독점**이다(2024 정규시즌 개막 3/23).
유료화로 티빙을 구독하지 않던 시청자가 유선 스포츠 채널로 옮겨가면서,
야구가 TV 뉴스를 잠식하는 구조 자체가 달라졌다.

그래서 `config.KBO_ERA_START` 이전 구간에서는 **야구 변수 22개를 결측으로 둔다.**
0 으로 두면 '경기가 없었다'는 다른 거짓 신호가 되므로 NaN 이어야 하고,
LightGBM 은 결측을 별도 분기로 처리한다. 야구 외 변수는 그대로 살아 있어
2023 년 데이터(236일)가 통째로 버려지지는 않는다.

**정확도로는 판정되지 않았다** (45 폴드).

| | MAE |
|---|---:|
| 시대 구분 전 (2023 야구 포함) | 0.1605 |
| 시대 구분 후 (2023 야구 결측) | 0.1615 |

차이 +0.0010, CI [−0.0009, +0.0028] → 0 포함. 다만 시즌 분해는 방향이 이치에 맞다.

| 구간 | 일수 | 전 → 후 |
|---|---:|---|
| 시즌 중 | 160 | 0.1446 → **0.1441** (+0.35%) |
| 비시즌 | 149 | 0.1776 → 0.1802 (−1.49%) |

야구 변수가 실제로 쓰이는 시즌 중에는 미세하게 나아지고, 도움될 이유가 없는 비시즌에
나빠진다. **손해가 없고 구조 변화는 실재하므로 유지한다.**

**한계.** 이 데이터로는 가설을 제대로 검증할 수 없다. 시청률이 2023-07 부터라
티빙 이전 시즌이 **107일(취소 22일)** 뿐이고, 시대별 잠식 효과 비교의 신뢰구간이
±7~9%p 로 벌어진다 — "차이가 없다"가 아니라 **"이 표본으로는 판정 불가"** 다.
그리고 종편 4사 시청률만 있어서, 뉴스에서 빠진 시청자가 스포츠 채널로 갔는지
확인할 수 없다. SPOTV·MBC스포츠+ 등의 시청률이 있으면 제대로 검증된다.

#### 일정은 이 프로젝트가 직접 수집한다

```bash
.venv/bin/python scripts/sync_kbo.py          # 2023~올해, 최근 2개월만 갱신
.venv/bin/python scripts/sync_kbo.py --all    # 전부 다시
```

지나간 달의 결과는 바뀌지 않으므로 최근 2개월과 미래 달만 다시 받는다.
2023-03 ~ 현재까지 **732일**을 확보했고, 외부 프로젝트 수집본을 완전히 포함한다
(외부에만 있는 날 0개, 자체에만 있는 날 8개).

빠진 것처럼 보이는 날은 실제 휴식기다 — 2023-07-14~20 올스타 브레이크,
2023-10-18 아시안게임 브레이크.

**수집이 조용히 잘렸던 적이 있다.** 네이버 API 의 `size` 기본값을 100 으로 뒀는데
한 달은 최대 ~130 경기라, 월 단위로 받으면 뒷부분이 사라졌다(613일만 확보).
에러 없이 데이터만 줄어들어 눈치채기 어려웠다 — 시청률 구간 대비 커버리지를
세어 보고 알았다. 지금은 600 으로 올렸다.

#### 당일 취소·시작 시각도 실시간으로

캐시에는 당일 우천취소가 없다 — 경기 1~2시간 전에 발표되기 때문이다.
`kbo.live_status(date)` 가 그 시점 현황(편성/취소/시작 시각/경기별 상태)을 준다.
대시보드에서 **당일 수정**을 켜면 자동 조회돼 사이드바에 뜬다.

```
편성 5경기 · 취소 없음 (조회 13:45)
적용값: 0경기 취소 · 시작 18:00 (실시간 확인)
```

순연·더블헤더로 편성표와 시작 시각이 달라져도 실측값이 반영된다.
응답은 5분 캐시하고, API 장애 시 캐시 → 휴리스틱 순으로 조용히 폴백한다.

### 방송 시간대별 경쟁 구조 — 19/21시대 버킷은 틀린 모델이다

처음엔 채널을 '19시대 / 21시대'로 나눴다. 이 데이터에서는 그게 맞지 않는다.
**평일과 주말의 경쟁 상대가 다르고, 편성이 3년 사이 여러 번 바뀌었다.**

현재 방송 구간 (사용자 실측):

| 채널 | 평일 | 주말 |
|---|---|---|
| 채널A 뉴스A | 18:55~19:55 (60분) | 18:25~19:00 (35분) |
| JTBC 뉴스룸 | 18:35~19:45 (70분) | 18:25~19:00 (35분) |
| MBN | 뉴스7 19:00~20:00 (60분) | **뉴스센터** 19:30~20:05 (35분) |
| TV조선 | 뉴스9 21:00~21:55 (55분) | **뉴스7** 18:57~19:57 (60분) |

MBN 주말(뉴스센터)과 TV조선 주말(뉴스7)은 **아예 다른 프로그램**이다.

그래서 시간대 버킷 대신 **실제 방송 구간의 겹침 비율**을 쓴다. 길이가 달라 겹침은
비대칭이다 — 짧은 프로그램이 긴 프로그램에 먹히는 쪽이 더 큰 값을 갖는다.

주말 겹침 행렬 (행 = 내 방송 시간 중 상대와 겹치는 비율):

| 나 \ 상대 | 채널A | JTBC | MBN | TV조선 |
|---|---:|---:|---:|---:|
| 채널A | — | **1.00** | 0.00 | 0.09 |
| JTBC | **1.00** | — | 0.00 | 0.00 |
| MBN | 0.00 | 0.00 | — | **0.77** |
| TV조선 | 0.05 | 0.00 | 0.45 | — |

**이게 내가 못 풀던 두 이상 현상을 설명한다.** MBN 은 주말에 19:30 으로 빠져
채널A·JTBC 와 겹침이 0 이 되므로 주말 시청률이 안 떨어지고(오히려 +4%),
TV조선은 평일 단독(겹침 0)에서 주말 정면충돌로 바뀌므로 −38% 떨어진다.
채널 고유의 시청층 특성이 아니라 **편성 구조**였다.

편성 이력은 `config.CHANNELS` 에 `SlotPeriod` 로 들어 있다 (JTBC 5회, 채널A 1회 변경).
날짜별 겹침은 `config.overlap_matrix()` 가 만든다.

### 편성 변경 효과 검정 — 채널A가 비켜준 자리

2026-01-10 채널A 주말이 19:00 → 18:25 로 옮기면서 TV조선 뉴스7(18:57~19:57) 구간을
비웠다(겹침 1.00 → 0.09). 이중차분(주말 − 평일)으로 재면:

| 채널 | ±28일 | ±42일 | ±56일 | ±120일 |
|---|---:|---:|---:|---:|
| **TV조선뉴스9** | **+0.84** | **+1.07** | **+0.99** | **+0.71** |
| JTBC뉴스룸 | −0.08 | +0.02 | −0.00 | +0.06 |
| 뉴스A | +0.06 | +0.02 | −0.02 | +0.01 |
| MBN뉴스7 | +0.01 | −0.08 | +0.09 | +0.09 |

TV조선만 창 크기에 무관하게 안정적이다. 편성 변경이 없던 43개 플라시보 날짜와 비교한
순열 검정에서 **p ≈ 0.023** 으로 유일하게 유의하다 (나머지 3사는 p ≥ 0.6).

주의: 원시 주말 변화는 +72% 였지만 그 대부분은 4사 공통 뉴스 국면 상승이다.
평일을 대조군으로 통제한 뒤 남는 순효과가 **+1.07%p** 다.

### 구조를 바로잡아도 예측은 나아지지 않았다

| 구성 | 피처 | MAE |
|---|---:|---:|
| 고정 19/21 슬롯 (틀린 모델) | 181 | 0.1577 |
| 실측 편성 · 전체 | 225 | 0.1603 |
| **실측 편성 · 파생 제외 (채택)** | **205** | **0.1586** |
| 4주 동요일평균 | — | 0.1680 |

부트스트랩 95% CI:
- 채택안 − 고정슬롯 = +0.0009 [−0.0016, +0.0032] → **동률**
- 채택안 − 4주평균 = −0.0094 [−0.0182, −0.0014] → **유의하게 우위**

편성 효과가 실재하는데도(위 DiD, p=0.023) 예측이 안 좋아진다. KBO 때와 같은 이유다 —
편성 변경은 3년에 6번뿐이라 배울 사례가 없고, 변경 후의 수준 변화는 이미 시차·이동평균
피처가 흡수한다. 225 피처에서 0.1603 까지 밀린 건 순수한 희석이었고, 남긴 것과 중복되는
파생 20개(`air_end`/`air_len`/`days_since_change`/`_apart_`)를 덜어내니 회복됐다.

**그래도 맞는 구조를 쓴다.** 정확도가 유의하게 나쁘지 않고, (1) 대시보드의 경쟁 구조
표시가 맞아야 하며, (2) 편성 변경 What-If 이 가능해지고, (3) 다음 개편 때 조용히
틀리지 않는다. **구조적 정확성과 예측 개선은 별개의 목표다.**

### 데이터 정제
- 달력상 빠진 날을 채워 **일자 연속성**을 확보한다. 그래야 `lag_7`이 실제로 지난주 같은 요일이 된다.
- 보간으로 채운 날은 **학습 타깃에서 제외**한다(피처 계산에는 사용). 채점에서도 뺀다.
- 메인 뉴스에 정확히 `0.000` 이 찍히면 시청률이 아니라 **결방**이다. 결측으로 처리한다.
- 표본 가중은 **주지 않는다.** 2024Q4 국면 변화 때문에 최근 데이터에 무게를 실어야 할 것 같지만, 재보면 반대다 (아래 튜닝 표). 표본이 1,100행뿐이라 과거를 깎아 유효 표본을 줄이는 손해가 더 크고, 수준 변화는 이미 lag/rolling 이 흡수한다.

#### 당일 취소는 네이버에서 실시간으로 가져온다

캐시 JSON 에는 당일 취소가 없다 — 경기 1~2시간 전에 발표되기 때문이다.
`kbo.live_status(date)` 가 네이버 스포츠 공개 API 를 직접 호출해 그 시점 현황을 준다
(인증 불필요, 캐시와 같은 소스·같은 형식).

대시보드에서 **당일 수정**을 켜면 대상일 현황이 사이드바에 자동으로 뜬다.

```
편성 5경기 · 취소 없음 (조회 13:41)      ← 아직 발표 전
3경기 취소 / 편성 5 · 조회 17:20         ← 일부 취소
전 경기 취소 (5/5) · 조회 17:05          ← washout
```

경기별 현황(시각·대진·구장·상태)도 펼쳐 볼 수 있고, `취소 경기 수 (직접 보정)` 에
숫자를 넣으면 발표 전 시나리오도 볼 수 있다. `-1` 이면 실시간 조회값을 그대로 쓴다.
응답은 5분 캐시한다.

| 취소 0경기 | 161 | 0.1608 | 0.1608 | +0.0% | 정확히 무변화 |
| 취소 1~2경기 | 11 | 0.1503 | 0.1493 | +0.6% | 0 포함 |

**1~2경기 취소로는 움직이지 않고, 전 구장급 취소에서만 나타난다.** 다섯 중 한둘이 빠져도
나머지가 중계되니 시청층이 이동하지 않는다는 뜻이고, 위 자연 실험의 용량-반응과 일치한다.

**다만 통계적으로 확증되지는 않았다.** 전 구장급 취소일이 179일 중 7일뿐이라 CI 가 0을

이득*은 아직 추정치다.

그래도 켜 둘 만하다. **취소가 없는 날엔 결과가 정확히 동일**하므로(161일에서 0.0000 차이)

있다.** 기상청 단기예보는 D+1~D+3 을 제공하므로 자연스러운 다음 단계다.

### 변수 묶음 애블레이션 — 세 번 재서 세 번 다른 답이 나왔다

`run_backtest.py --ablation` 로 그룹을 하나씩 빼며 오차 변화를 쟀다. **결과가 재현되지 않는다.**

| 실행 | 폴드 | 결론 |
|---|---:|---|
| 1차 | 5 | `slot` 만 기여(+2.18%), KBO 두 그룹은 빼는 게 나음(−0.98/−2.45%) |
| 2차 확인 | 10 | KBO 를 빼면 오히려 **+2.42% 나빠짐** (CI [+0.0005, +0.0076], 1차와 반대) |
| 3차 | 6 | **모든 그룹**이 빼는 게 나음 (slot −2.34%, holiday −2.08%, kbo −1.62%, astro −1.11%, weather −0.53%) |

3차에서는 1차에서 유일하게 기여한다던 `slot` 이 가장 크게 "빼는 게 나은" 그룹이 됐다.
폴드 세트가 바뀌면 절대 수준도 크게 달라진다 — 같은 전체 피처 모델이
6폴드에서 MAE 0.1270, 26폴드에서 0.1654 다.

**그래서 이 방법으로는 아무것도 결정하지 않는다.** 5~10 폴드 애블레이션은 이 데이터에서
변수 그룹의 기여를 판정할 검정력이 없다. 한때 "시간대 경쟁 피처만 뚜렷하게 기여한다"고
적었지만 근거가 사라졌으므로 철회한다.

변수를 빼려면 **같은 폴드 세트에서 반복 측정하고 부트스트랩 CI 로 판정**해야 한다.
실제로 그렇게 확인한 건 두 건뿐이다.

| 판정 | 방법 | 결과 |
|---|---|---|
| KBO 그룹 유지 | 10폴드 + CI | 빼면 +2.42% 나빠짐, CI 0 안 넘음 → **유지** |
| `sched_extra` 제외 | 26폴드 + CI | 빼면 0.1603 → 0.1586, 전체 피처와 동률 → **제외**(중복 제거) |

`--drop <그룹> --folds 45` 로 언제든 더 많은 폴드에서 다시 잴 수 있다.

### 설정 튜닝 (`scripts/tune.py`, 6 폴드)

| 설정 | MAE | vs 지난주 동요일 |
|---|---:|---:|
| **l1 · 가중 없음** | **0.1449** | +13.3% |
| l1 · 반감기 400일 | 0.1485 | +11.1% |
| l1 · 반감기 180일 | 0.1500 | +10.2% |
| l2 · 반감기 400일 | 0.1590 | +4.8% |

두 가지가 나온다. **손실은 `l1`(MAE)이 `l2`보다 확실히 낫다** — 급등 이상치가 잦아
제곱 손실이 끌려간다. 그리고 **가중을 세게 줄수록 단조적으로 나빠진다.** 직관과 반대라
기본값을 균등 가중으로 바꿨다.

### 변수 기여도 (홀드아웃 순열 중요도)

채널A 뉴스A D+1 기준 상위 변수: `뉴스A_roll_mean_7` → **`kbo_games`** → **`kbo_games_19`**
→ `뉴스A(2049)_lag_1` → `JTBC뉴스룸(2049)_lag_21`.
**야구 관련 변수가 2·3위**로, 19시대 뉴스가 야구 중계에 잠식된다는 가설이 실제로 확인된다.

What-If 로 측정한 효과 크기 (7일 평균):

| 시나리오 | 채널A | JTBC | MBN | TV조선 |
|---|---:|---:|---:|---:|
| 야구 전 경기 취소 | +0.086 | +0.070 | +0.112 | +0.043 |
| 평일 18:30 정상 진행 | −0.035 | −0.039 | −0.027 | −0.006 |

19시대 3사가 21시대 TV조선보다 2~10배 크게 반응한다 — 시간대 겹침 구조가 그대로 나온다.

시청률처럼 요일 효과가 지배적인 계열에서는 `snaive_7`·`dow_mean_4` 가 꽤 강한 상대다.
**이 둘을 못 이기면 모델을 쓸 이유가 없다.** 성능 표는 대시보드 `모델 성능` 탭에서도 볼 수 있다.

## 4. What-If 시뮬레이터

사이드바에서 조건을 바꾸면 **기본 예측 대비 변화량**을 계산한다.

- **KBO 편성** — 전 경기 우천취소 / 평일 18:30 / 주말 17:00
- **평년 대비 기온** — ±10°C
- **대형 속보 국면 강도** — 0(평시) ~ 1(과거 대형 이슈 수준)

야구처럼 관측이 충분한 변수는 신뢰할 만하다. 속보 국면은 사례가 적고 `events.csv` 구간이
시청률 급등에서 역으로 탐지된 것이라 **방향성 참고용**으로만 봐야 한다. 이 변수는 백테스트에서
제외해 성능 수치가 부풀지 않게 했다.

### 시나리오 링크 공유

조작한 시나리오는 URL 에 그대로 실린다. 링크를 넘기면 같은 화면이 열린다.

```
http://localhost:8501/?view=1&kbo=none&metric=2049      # 우천취소 시 2049 시청률
http://localhost:8501/?view=2                            # 모델 성능 화면
```

`view` 0=예측 1=What-If 2=모델 성능 3=데이터 · `kbo` auto|none|weekday_1830|weekend_1700
· `temp` −10~10 · `event` 0~1 · `metric` 가구|2049

## 5. 속보 국면 — 유형을 나눠야 한다

`data/events.csv` 에 사건 구간을 등록하면 모델이 별도 변수로 학습한다.

| 구간 | 사건 | 유형 |
|---|---|---|
| 2023-09-17 ~ 09-26 | 이재명 체포동의안 가결(9-21)·구속영장 기각(9-27) | `이재명_사법` |
| 2024-12-04 ~ 12-19 | 12·3 비상계엄 → 탄핵소추안 가결(12-14) | `윤석열_사법` |
| 2025-05-06 ~ 05-10 | 김문수·한덕수 단일화 협상(5-9) | `대선_정국` |
| 2026-02-16 ~ 02-20 | 윤석열 내란 우두머리 1심 무기징역 선고(2-19) | `윤석열_사법` |

### 왜 유형을 나누나 — 채널별 우위가 뒤바뀐다

**국면 직전 8주 같은 요일** 대비 배율:

| 국면 | 채널A | JTBC | MBN | TV조선 |
|---|---:|---:|---:|---:|
| 윤석열_사법 (3개 구간) | 0.99 | **1.63** | 1.03 | 1.00 |
| 이재명_사법 (1개 구간) | 1.33 | 1.21 | **1.47** | 0.94 |
| 대선_정국 (1개 구간) | 1.13 | 1.24 | 1.11 | 0.93 |

윤석열 사법 국면에선 **JTBC 만** 뛰고 나머지는 제자리다. 이재명 사법 국면에선
MBN·채널A 가 앞서고 JTBC 가 뒤진다. 하나의 변수에 뭉쳐두면 서로 상쇄된다.

#### 기준선을 잘못 잡아 한 번 틀렸다

처음엔 **전 기간 요일평균**을 기준선으로 썼고, 그때는 이렇게 나왔다.

| 2023-09 (이재명) | 전 기간 평균 대비 | 직전 8주 대비 |
|---|---:|---:|
| 채널A | 1.56 | 1.33 |
| JTBC | **0.84** | **1.21** |
| TV조선 | 1.37 | 0.94 |

"이재명 국면엔 JTBC 가 내려간다"고 여러 번 말했는데 **틀렸다.** JTBC 의 0.84 는 국면
효과가 아니라 **추세 효과**였다 — 2023년 9월 JTBC 는 1.78% 로 3년 평균보다 한참 낮은
시기였고(2024Q4 에 2배로 뛰기 전), 전 기간 평균과 비교하니 내려간 것처럼 보였다.

배율은 **모델 예측값에 곱하는 값**이고 모델 예측은 최근 수준을 이미 반영하므로,
'직전 대비 얼마나 뛰었나'가 맞는 기준이다. 2025-01 구속영장 국면도 전 기간 대비
2.78배 → 직전 8주 대비 **1.47배**로 정상화됐다(이미 높던 탄핵 정국 위의 스파이크였다).

#### 같은 유형 안에서도 편차가 크다

윤석열_사법 JTBC 배율: 2024-12 **1.89배** · 2025-01 1.47배 · 2026-02 1.52배.
계엄 당시가 가장 컸고 이후 사법 절차는 그보다 작다. 평균 하나로 대표하기 어렵다 —
UI 에 구간별 범위를 함께 표시한다.

### 모델이 학습할 수 없어서, 실측 배율을 직접 곱한다

유형별 변수를 만들어 학습시켜 봤지만 **실패했다.** 원인이 명확하다.

| 모델 | is_news_event | event_윤석열 | event_이재명 | event_대선 |
|---|---:|---:|---:|---:|
| 뉴스A | 0 | 0 | 0 | 0 |
| JTBC뉴스룸 | 6 | 2 | 0 | 0 |
| MBN뉴스7 | 0 | 0 | 0 | 0 |
| TV조선뉴스9 | 0 | 0 | 0 | 0 |

(트리가 그 변수로 분기한 횟수). **`min_child_samples=20` 인데 양성 일수가 윤석열 21일,
이재명 10일, 대선 5일이다.** 분기 한쪽에 최소 20개가 있어야 하니 물리적으로 나눌 수 없다.
채널A·MBN·TV조선 모델은 이벤트 변수를 한 번도 쓰지 않았고, 세 유형을 켜도 전부
JTBC 만 조금 오르는 같은 결과가 나왔다 — 이재명 국면은 실제와 정반대였다.

모델이 학습 못 하는 걸 학습한 척할 수는 없으므로, **과거 실측 배율을 예측값에 곱하는**
방식으로 바꿨다 (`forecast.event_multipliers`).

| 국면 | 채널A | JTBC | MBN | TV조선 |
|---|---:|---:|---:|---:|
| 윤석열_사법 | 0.94 | **2.01** | 1.02 | 0.84 |
| 이재명_사법 | **1.56** | 0.84 | **1.49** | **1.37** |
| 대선_정국 | 0.95 | 1.41 | 1.01 | 0.85 |

**이 값은 모델 출력이 아니다.** 과거 같은 유형 국면에서 요일 보정 후 관측된 평균 배율이며,
UI 에도 그렇게 표시한다. 유형별 변수는 학습에서 제외했다(`event_type` 그룹) — split 이
0 이면 희석만 시킨다. `is_news_event` 는 JTBC 가 실제로 쓰고 있어(split 16회) 남겼다.
과거 급등을 날씨나 야구 탓으로 돌리지 않게 막아주는 역할이다.

### 강도 슬라이더를 없앤 이유

처음엔 0~1 강도 슬라이더를 뒀는데, 재보니 **0.2 든 1.0 이든 결과가 완전히 같았다.**
학습 데이터에서 이 값은 0(1,088일) 아니면 1(36일) 뿐이라 트리에겐 0.5 부근 분기 하나가
전부다. 지금은 배율이 과거 평균 하나뿐이라 눈금을 만들 근거 자체가 없다.

### 자동 탐지 — 기준선 고르는 데 세 번 실패했다

```bash
.venv/bin/python scripts/detect_events.py
```

`label` 과 `type` 은 사람이 채워야 한다. 기준선을 어떻게 잡느냐로 결과가 완전히 달라졌다.

| 시도 | 문제 |
|---|---|
| 후행 28일 중앙값 | 수 주 이어지는 국면에서 기준선이 같이 올라가, 국면 중간의 사소한 요철만 골라낸다 (2025-07 오탐) |
| 후행 30~120일 중앙값 | 3년간 시청률이 절반으로 떨어지는 추세 탓에 과거가 체계적으로 높아, 국면이 아니라 수준 변화를 잡는다 (128~166일 구간) |
| 전 기간 요일평균 + 중심 중앙값 | 2026-01-10 채널A 편성 변경으로 오른 TV조선 주말을 이벤트로 오인, 토요일이 무더기로 잡힌다 |
| **같은 요일끼리 중심 중앙값 (13주)** | **추세·요일효과·편성변경을 모두 흡수. 알려진 4개 국면을 모두 포착하면서 탐지일 44일** |

**검증은 이벤트 없이 돌린다** (`events=None`). 구간이 시청률 급등에서 역으로 탐지된
것이라 성능 수치가 부풀 수 있기 때문이다. 이 변수의 값어치는 정확도가 아니라
"윤석열 국면이 오면 어느 채널이 오르나"를 시뮬레이션할 수 있다는 데 있다.

## 7. 이 프로젝트에서 데인 것들

같은 실수를 반복하지 않으려고 남긴다.

**① 원본 데이터에 사후 정보가 섞여 있었다.** 네이버 일정 JSON 의 `cancel` 은 경기가
끝난 뒤의 결과다. `kbo_games`(취소되지 않은 경기 수)를 그대로 쓰면 "내일 비가 와서
5경기가 다 취소된다"를 미리 아는 모델이 된다. 2026-08-28 이 그런 날이었다.
→ 경기 수·시작시각은 **편성 기준**으로 통일하고, 취소만 `as_of` 로 게이팅한다.

**② 누수를 막다가 없는 제약을 만들었다.** `as_of` 를 마지막 관측일로 못 박으니
"예측은 전날 한 번만 낸다"가 돼 버렸다. 실제로는 KBO 가 17시 전후에 취소를 발표하고
뉴스는 18:20~21:55 에 나가므로 그 사이에 고칠 수 있다. → 두 모드로 분리.

**③ 학습과 추론에서 변수의 의미가 달랐다.** ①을 고치기 전에는 학습이 사후값(실제 진행
경기 수), 추론이 편성값을 쓰고 있었다. 에러가 나지 않아 조용히 지나간다. 통일 후
재학습하니 같은 상황의 당일 수정 폭이 MBN 기준 +4.9% → +12.4% 로 두 배가 됐고,
순열 중요도 1위도 `kbo_games`(요일과 중복) 에서 `kbo_cancelled` 로 바뀌었다.

**④ 그럴듯한 설명이 붙은 측정을 믿었다.** 5 폴드 애블레이션이 "KBO 변수를 빼는 게
낫다"고 했고 설명도 완벽했다(요일과 공선적이다, 추론 시점엔 상수다). 10 폴드로
확인하니 반대였다. → 재현되지 않는 측정으로 피처를 버리지 않는다.

**⑤ 점추정을 확정처럼 말했다.** "washout 날 +16% 개선"은 대상일 7일에서 나온 값이고
CI 가 0을 포함한다. 표본을 늘리자 +11.6% 로 줄었다. → 조건부 결과에는 CI 를 붙인다.

**⑥ 도메인 구조를 데이터에서 유추하려 했다.** '주말 낙폭이 채널마다 다르다'를 두고
시청층 특성으로 설명했었다. 실제 원인은 편성이었다 — MBN 은 주말에 19:30 뉴스센터로
빠지고 TV조선은 18:57 뉴스7 로 내려온다. 그리고 JTBC 는 3년 사이 5번 시간을 옮겼다.
**데이터만 봐서는 절대 알 수 없는 것들이고, 아는 사람에게 물어야 했다.**
19/21시대 버킷이라는 초기 설계 자체가 틀렸었다.

**⑦ 원시 변화량으로 인과를 말할 뻔했다.** 채널A 주말 개편 후 TV조선 주말이 +72% 였지만
대부분은 4사 공통 뉴스 국면 상승이었다. 평일을 대조군으로 통제하니 순효과는 +1.07%p.
반대로, 주 단위 그래프에 불연속이 안 보인다고 "편성 효과가 아니다"라고 한 것도 성급했다
— 이중차분은 그 추세를 이미 통제한다. → 원시 변화도, 눈으로 본 추세도 아니고,
**대조군을 세우고 플라시보로 검정**해야 한다.

**⑧ 구조적 정확성과 예측 개선을 같은 것으로 봤다.** 편성 모델을 제대로 고치고 나서도
MAE 는 나아지지 않았다(0.1577 → 0.1586, 동률). 효과가 실재해도(DiD p=0.023) 사례가
6번뿐이면 모델은 배울 수 없고, 수준 변화는 이미 시차 피처가 흡수한다.
그래도 맞는 구조를 쓴다 — 이유는 정확도가 아니라 해석·시뮬레이션·유지보수다.

같은 일이 **세 번** 있었다: KBO 편성, 실측 방송구간, 기상. 전부 "구조는 맞췄는데
예측은 그대로"였다. 이 데이터에서 예측력의 대부분은 시차·이동평균·요일이 이미
흡수하고 있고, 외생 변수가 비집고 들어갈 틈이 거의 없다.

**외생 변수를 추가하기 전에 상한부터 계산해 보는 편이 낫다.** 기상의 경우
당일 수정 이득(+13.1%) × 예보 포착률(46.7%) × 사건 빈도(4%) ≈ 0.25% 로,
검출 가능한 크기가 아니라는 걸 측정 전에 알 수 있었다.

**⑨ 변수를 만들어 넣으면 모델이 쓸 거라고 가정했다.** 사건 유형별 변수를 만들고
학습시킨 뒤 시나리오를 돌렸더니 세 유형이 전부 같은 결과를 냈다. 확인해 보니
`min_child_samples=20` 에 걸려 양성 5~21일짜리 변수로는 트리가 **분기조차 못 했다**
(split 횟수 0). 만들었다고 쓰이는 게 아니다. → 희소한 변수를 넣었으면
`booster_.feature_importance('split')` 로 실제로 쓰이는지 확인할 것.
쓰이지 않는다면 모델 밖에서(실측 배율 등) 처리하는 편이 정직하다.

**⑩ 파이프라인을 실제로 돌려보기 전엔 모른다.** `daily_update.sh` 를 처음 실행하니
기상 캐시가 **1,186일 → 401일** 로 잘렸다. `build_cache` 가 파일을 통째로 덮어쓰는데
일일 갱신은 최근 400일만 넘기기 때문이다. 매일 아침 자동 실행됐다면 에러 없이
과거를 계속 날렸을 것이다. → 증분 갱신 스크립트는 **반드시 한 번 실행해 보고**
누적 결과를 확인할 것. 지금은 기존 파일과 병합한다.

이번 프로젝트에서 잡은 '조용한' 버그 세 개는 전부 예외를 던지지 않고 데이터만
줄어드는 종류였다.

| 버그 | 증상 | 발견 경로 |
|---|---|---|
| `drop_duplicates` 가 같은 시각·조건 경기를 병합 | 하루 5경기 → 2경기 | 원본 JSON 대조 |
| 네이버 API `size` 기본 100 | 월 단위 수집이 뒷부분 잘림 (613일) | 커버리지 계산 |
| `build_cache` 덮어쓰기 | 기상 1,186일 → 401일 | **실제 실행** |

공통점은 **행 수를 세어 보기 전엔 알 수 없었다**는 것이다. 외부 데이터를 붙일 때마다
'기대하는 커버리지'를 명시적으로 확인하는 습관이 필요하다.

**⑪ 판정의 표본 크기를 먼저 확인하지 않았다.** 이 프로젝트의 판정 대부분을
26폴드(대상일 179일) 한 번으로 내렸다. 그런데 데이터가 하루 늘었을 뿐인데
"4주평균 대비 +5.6% 유의" 가 "+3.6% 유의하지 않음" 으로 뒤집혔고, 애블레이션은
세 번 재서 세 번 다른 답을 냈다. 45폴드(309일)로 늘리자 안정됐다(+6.9%, CI 0 안 넘음).

→ **판정 전에 그 방법의 검출력부터 확인할 것.** 폴드를 늘려도 결론이 안 바뀌는지,
